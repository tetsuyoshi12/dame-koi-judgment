# 要件定義書：ダメ恋プロフィール裁判所

## Intent Analysis（意図分析）

### ユーザーリクエスト
AWS Summit Japan 2026 ハッカソン向けの「人をダメにする」サービスの開発

### リクエストタイプ
新規プロジェクト（Greenfield）

### スコープ推定
複数コンポーネント（フロントエンド + バックエンド + AI統合）

### 複雑度推定
中程度 - ハッカソンデモとして適切な範囲、技術的には標準的なサーバーレス構成

---

## プロジェクト概要

### サービス名
**「ダメ恋プロフィール裁判所」**

### コンセプト
マッチングアプリで成果が出ないユーザーに対し、AWSのAIが「立派な人を演じる努力」を有罪判決し、虚飾を脱ぎ捨ててダメな本来の自分のままで勝てる戦略（新プロフィール）を発行する、自己研鑽社会へのカウンター型婚活ピボットサービス。

### ハッカソンテーマとの整合性
**「人をダメにする」メカニズム**:
- 「立派な人を演じる」努力を奪う
- 「自分磨き」の呪縛を解体
- 「成長したフリ」の演技を不要にする
- 「こうあるべき」の規範意識を放棄させる

→ ユーザーから自己改善の意欲を奪い、ダメなまま生きることを推奨する

## 機能要件

### Must Have（ハッカソンデモまでに必須）

#### 1. 4フェーズの入力・出力インターフェース

**Phase 1: 虚飾の入力**
- 通常のマッチングアプリ風フォーム
- 入力項目：
  - 自己紹介文（テキストエリア）
  - 趣味・特技（テキストエリア）
  - 理想の相手像（テキストエリア）
  - 休日の過ごし方（テキストエリア）

**EARS記法による要件**:
- **REQ-F1.1**: ユーザーがPhase 1画面にアクセスする場合、システムはマッチングアプリ風の入力フォームを表示しなければならない
- **REQ-F1.2**: ユーザーが自己紹介文を入力する場合、システムはテキストエリア形式で入力を受け付けなければならない
- **REQ-F1.3**: ユーザーが趣味・特技を入力する場合、システムはテキストエリア形式で入力を受け付けなければならない
- **REQ-F1.4**: ユーザーが理想の相手像を入力する場合、システムはテキストエリア形式で入力を受け付けなければならない
- **REQ-F1.5**: ユーザーが休日の過ごし方を入力する場合、システムはテキストエリア形式で入力を受け付けなければならない
- **REQ-F1.6**: ユーザーがPhase 1の入力を完了する場合、システムはPhase 2画面に遷移しなければならない

**Phase 2: 本音の入力**
- 5段階評価 + 自由記述形式
- 入力項目：
  - ズボラ度（1-5スライダー）
  - 実際の休日の過ごし方（テキストエリア）
  - サボり癖・怠惰な習慣（テキストエリア）
  - 本当は面倒だと思っていること（テキストエリア）

**EARS記法による要件**:
- **REQ-F2.1**: ユーザーがPhase 2画面にアクセスする場合、システムは本音入力フォームを表示しなければならない
- **REQ-F2.2**: ユーザーがズボラ度を入力する場合、システムは1から5までのスライダー形式で入力を受け付けなければならない
- **REQ-F2.3**: ユーザーが実際の休日の過ごし方を入力する場合、システムはテキストエリア形式で入力を受け付けなければならない
- **REQ-F2.4**: ユーザーがサボり癖・怠惰な習慣を入力する場合、システムはテキストエリア形式で入力を受け付けなければならない
- **REQ-F2.5**: ユーザーが本当は面倒だと思っていることを入力する場合、システムはテキストエリア形式で入力を受け付けなければならない
- **REQ-F2.6**: ユーザーがPhase 2の入力を完了する場合、システムはバックエンドAPIにPhase 1とPhase 2のデータを送信しなければならない
- **REQ-F2.7**: システムがバックエンドAPIにデータを送信する場合、システムはローディング表示を表示しなければならない

**Phase 3: 論理的否定（結果表示）**
- AIによる矛盾の指摘
- 学術的根拠に基づく戦略破綻の証明
- 「頑張っても無駄」の宣告
- 冷徹な裁判官トーンでの表示

**EARS記法による要件**:
- **REQ-F3.1**: システムがバックエンドからPhase 3の結果を受信する場合、システムは画面を暗転させなければならない
- **REQ-F3.2**: システムが画面を暗転させる場合、システムは2〜3秒間の無音状態を維持しなければならない
- **REQ-F3.3**: システムが無音状態を終了する場合、システムは論理的否定文を浮かび上がらせて表示しなければならない
- **REQ-F3.4**: システムが論理的否定文を表示する場合、システムはAIによる矛盾の指摘を含めなければならない
- **REQ-F3.5**: システムが論理的否定文を表示する場合、システムは学術的根拠に基づく戦略破綻の証明を含めなければならない
- **REQ-F3.6**: システムが論理的否定文を表示する場合、システムは「頑張っても無駄」の宣告を含めなければならない
- **REQ-F3.7**: システムが論理的否定文を表示する場合、システムは冷徹な裁判官トーンで表示しなければならない
- **REQ-F3.8**: ユーザーがPhase 3の表示を確認する場合、システムはPhase 4画面に遷移するボタンを表示しなければならない

**Phase 4: 改善案発行（結果表示）**
- ダメさを魅力に翻訳した説明
- 新ターゲット層の定義
- 新プロフィール文（150〜300文字）
- 期待マッチング率（AIが生成した説得力のある数値）

**EARS記法による要件**:
- **REQ-F4.1**: ユーザーがPhase 4画面にアクセスする場合、システムは改善案を表示しなければならない
- **REQ-F4.2**: システムが改善案を表示する場合、システムはダメさを魅力に翻訳した説明を含めなければならない
- **REQ-F4.3**: システムが改善案を表示する場合、システムは新ターゲット層の定義を含めなければならない
- **REQ-F4.4**: システムが改善案を表示する場合、システムは150〜300文字の新プロフィール文を含めなければならない
- **REQ-F4.5**: システムが改善案を表示する場合、システムは期待マッチング率を含めなければならない
- **REQ-F4.6**: システムが新プロフィール文を表示する場合、システムはPhase 1で入力した文言に抹消線を引いて表示しなければならない
- **REQ-F4.7**: システムが抹消線を表示する場合、システムはCSSアニメーションで視覚的な転換を演出しなければならない

#### 2. Amazon Bedrock統合

**モデル**: Claude Opus 4.7（または利用可能な最新Claude）

**プロンプト設計**: 
- 1つのプロンプトで以下をすべて実行：
  - Phase 1とPhase 2の矛盾検知
  - 学術的根拠付き論理的否定文生成（行動心理学・統計データ・進化学的視点の用語を含む）
  - ダメさ翻訳（弱点 → 魅力）
  - 新プロフィール文発行
  - 期待マッチング率の生成

**論理的否定の3要素**:
1. 事実の指摘（Phase 1とPhase 2の乖離）
2. 学術的根拠（行動心理学・統計・進化学のいずれか）
3. 甘い期待の棄却（努力の剥奪）

**EARS記法による要件**:
- **REQ-F5.1**: システムがPhase 1とPhase 2のデータを受信する場合、システムはAmazon Bedrock APIを呼び出さなければならない
- **REQ-F5.2**: システムがBedrock APIを呼び出す場合、システムはClaude Opus 4.7（または利用可能な最新Claude）を使用しなければならない
- **REQ-F5.3**: システムがBedrockにプロンプトを送信する場合、システムはPhase 1とPhase 2の矛盾を検知するよう指示しなければならない
- **REQ-F5.4**: システムがBedrockにプロンプトを送信する場合、システムは学術的根拠付き論理的否定文を生成するよう指示しなければならない
- **REQ-F5.5**: システムが論理的否定文を生成する場合、システムは行動心理学・統計データ・進化学的視点のいずれかの用語を含めなければならない
- **REQ-F5.6**: システムが論理的否定文を生成する場合、システムは事実の指摘・学術的根拠・甘い期待の棄却の3要素を含めなければならない
- **REQ-F5.7**: システムがBedrockにプロンプトを送信する場合、システムはダメさを魅力に翻訳するよう指示しなければならない
- **REQ-F5.8**: システムがBedrockにプロンプトを送信する場合、システムは新プロフィール文を発行するよう指示しなければならない
- **REQ-F5.9**: システムがBedrockにプロンプトを送信する場合、システムは期待マッチング率を生成するよう指示しなければならない
- **REQ-F5.10**: システムがBedrockからレスポンスを受信する場合、システムは15秒以内にフロントエンドに結果を返さなければならない
- **REQ-F5.11**: システムがBedrockのレスポンスが15秒を超える場合、システムはタイムアウトエラーを返さなければならない

#### 3. UI/UX演出

**クライマックス演出**: 視覚的な転換
- Phase 1で入力したキラキラ言葉に抹消線が引かれる
- 改善案として新しいプロフィール文が上書きされる
- CSSアニメーションで実装

**トーン**: 冷徹な裁判官
- 感情を排した法廷風の文体
- 学術用語・統計用語で客観性を演出
- 判決文形式での結果表示

**結果表示演出**:
- 画面暗転 → 2〜3秒の無音 → 結果テキストが浮かび上がる

**EARS記法による要件**:
- **REQ-F6.1**: システムがPhase 4で新プロフィール文を表示する場合、システムはPhase 1の入力文に抹消線を引かなければならない
- **REQ-F6.2**: システムが抹消線を表示する場合、システムはCSSアニメーションで視覚的な転換を演出しなければならない
- **REQ-F6.3**: システムがPhase 3の結果を表示する場合、システムは画面を暗転させなければならない
- **REQ-F6.4**: システムが画面を暗転させる場合、システムは2〜3秒間待機しなければならない
- **REQ-F6.5**: システムが待機時間を終了する場合、システムは結果テキストを浮かび上がらせて表示しなければならない
- **REQ-F6.6**: システムが論理的否定文を表示する場合、システムは冷徹な裁判官トーンの文体を使用しなければならない
- **REQ-F6.7**: システムが論理的否定文を表示する場合、システムは判決文形式で表示しなければならない

#### 4. 新プロフィール文のコピー機能
- ワンクリックでクリップボードにコピー
- コピー完了のフィードバック表示

**EARS記法による要件**:
- **REQ-F7.1**: ユーザーがコピーボタンをクリックする場合、システムは新プロフィール文をクリップボードにコピーしなければならない
- **REQ-F7.2**: システムがクリップボードにコピーする場合、システムはコピー完了のフィードバックメッセージを表示しなければならない
- **REQ-F7.3**: システムがフィードバックメッセージを表示する場合、システムは2〜3秒後に自動的に非表示にしなければならない

## 技術要件

### フロントエンド
- **フレームワーク**: Next.js（React）
- **実装範囲**: 主要機能のみ
  - Phase 1, 2の入力フォーム
  - Phase 3, 4の結果表示
  - 演出は最小限（暗転 → テキスト表示、抹消線アニメーション）
- **スタイリング**: CSS Modules または Tailwind CSS
- **デプロイ**: Vercel または S3 + CloudFront

### バックエンド
- **アーキテクチャ**: サーバーレス
  - API Gateway（REST API）
  - Lambda（Node.js または Python）
  - Amazon Bedrock（Claude Opus 4.7）
- **IaC**: AWS CDK（TypeScript）
- **データストレージ**: なし（セッション単位で完結）

- [ ] 審査員が「人をダメにする」コンセプトを理解できる

## リスクと対策

### 技術的リスク

**リスク1**: Bedrock（Claude Opus 4.7）が利用可能なリージョンが限定的
- **対策**: 事前にリージョン可用性を確認、代替モデル（Claude Sonnet）も検討

**リスク2**: プロンプトがAI Safetyフィルターに引っかかる
- **対策**: 学術用語・統計用語で攻撃性を客観的事実報告に偽装

**リスク3**: Bedrockのレスポンスが15秒を超える
- **対策**: プロンプトを最適化してトークン消費を削減、ローディング表示で体感時間を短縮

### スケジュールリスク

**リスク4**: 2週間で実装が完了しない
- **対策**: MVP（Minimum Viable Product）を明確化、演出は最後に実装

**リスク5**: チームメンバーの稼働が確保できない
- **対策**: 役割分担を明確化、並行作業可能な設計

## Extension Configuration

| Extension | Enabled | Decided At |
|---|---|---|
| Security Baseline | No | Requirements Analysis |
| Property-Based Testing | No | Requirements Analysis |

**理由**: ハッカソンプロトタイプのため、セキュリティルールとPBTルールは適用しない。デモ動作確認と主要機能の単体テストに注力する。
