# 要件定義書

## インテント分析サマリー

- **ユーザーリクエスト**: 「ダメ恋プロフィール裁判所」— マッチングアプリで成果が出ないユーザーに対し、AIが「立派な人を演じる努力」を有罪判決し、ダメなまま勝てる新プロフィールを発行するWebサービス
- **リクエストタイプ**: 新規プロジェクト（Greenfield）
- **スコープ推定**: 複数コンポーネント（フロントエンド + API Gateway + Lambda + Bedrock + S3 + CloudFront）
- **複雑度推定**: Moderate（AIプロンプトエンジニアリング + 演出UI + AWSインフラ）

---

## 確定した技術スタック

| 項目 | 決定内容 |
|------|---------|
| フロントエンド | React（SPA） |
| ホスティング | AWS S3 + CloudFront |
| バックエンド | Python Lambda |
| AI エンジン | Amazon Bedrock（Claude Opus 4.7） |
| Bedrock リージョン | ap-northeast-1（東京） |
| データ保存 | 匿名化して永続保存（DynamoDB or S3） |
| セキュリティ拡張 | スキップ（PoC/ハッカソン用途） |
| PBT拡張 | Partial（純粋関数・シリアライゼーションのみ） |
| AIキャラクター | 無機質なモノリス（SF的・冷徹なAIイメージ） |
| クライマックス演出 | 案A（抹消線 → 上書き） |
| 学術視点バランス | 均等（行動心理学 / 統計 / 進化学 各33%） |

## 機能要件

### FR-01: 4フェーズ入力インターフェース

**Phase 1 — 虚飾の入力**
- マッチングアプリ風フォームUI
- 入力項目：自己紹介文、趣味・休日の過ごし方、理想の関係性、アピールポイント
- 「立派な自分」として書いた内容を収集

**Phase 2 — 本音の入力**
- Phase 1 の入力内容をもとに、対応する「本音」項目を動的生成する
  - 例：Phase 1 で「週末はジムでリフレッシュ」と入力 → Phase 2 で「実際の週末の過ごし方は？」を生成
  - 例：Phase 1 で「互いに高め合える関係が理想」と入力 → Phase 2 で「本音の理想の関係性は？」を生成
  - 例：Phase 1 で「読書・映画鑑賞が趣味」と入力 → Phase 2 で「実際に最後に本を読んだのはいつ？」を生成
- 各項目は「5段階評価スライダー」または「自由記述」のいずれかで回答
  - 定量化できる内容（頻度・度合い）はスライダー
  - 具体的な実態（何をしているか）は自由記述
- Phase 1 の項目数に応じて Phase 2 の項目数も変動（1対1対応）
- UI上で Phase 1 の虚飾テキストを薄く表示し、「これの本当のところは？」という形式で提示
- 「AIにだけ教える本当の自分」として実態を収集

**Phase 3 — 論理的否定（努力の剥奪）**
- Bedrock（Claude Opus 4.7）による矛盾検知
- Phase 1 と Phase 2 の乖離を具体的に指摘
- 3つの学術的視点（行動心理学・統計データ・進化学）を均等に使用した否定文生成
- 「冷徹な裁判官」トーン（法廷風文体）
- 「頑張っても無駄」の宣告（努力の剥奪）

**Phase 4 — 改善案発行（ダメなまま勝つ戦略）**
- ダメさ翻訳テーブル（弱点 → 魅力への変換）
- 新ターゲット層の定義（年齢・属性・志向）
- 新プロフィール文の自動生成（150〜300文字、ダメさを隠さない文体）
- 期待マッチング率（市場適合性スコア）の表示

### FR-02: Bedrock 統合

- Claude Opus 4.7 を ap-northeast-1 で使用
- **Phase 2 項目生成**: Phase 1 の入力を受け取り、対応する本音質問リストを生成するプロンプト（軽量）
- **矛盾検知・否定文生成**: Phase 1/2 の対応ペアから矛盾を検知し、学術的根拠付き否定文を生成
- 矛盾検知 → 学術的否定文生成 → ダメさ翻訳 → 新プロフィール発行をワンプロンプトで実現
- プロンプトに3視点（行動心理学・統計・進化学）を均等に組み込む
- AI Safety 対応：学術用語・統計用語・進化学用語で攻撃性を客観的事実報告として表現
- **APIエンドポイント構成**:
  - `POST /generate-questions`（Phase 1 入力 → Phase 2 質問リスト生成）
  - `POST /analyze`（Phase 1/2 の対応ペア → Phase 3/4 の結果生成）

### FR-03: 演出UI

- **暗転演出**: Phase 3 表示時に画面暗転 → 2〜3秒の無音 → 否定文テキストが浮かび上がる
- **クライマックス演出（案A）**: 入力したキラキラ言葉に抹消線が引かれ、改善案として上書きされるアニメーション
- **テキストアニメーション**: 否定文が一文字ずつ表示される（Should Have）
- **新プロフィール文コピー機能**（Should Have）

### FR-04: データ収集・保存

- 匿名化されたプロフィールデータ（虚飾・本音・否定文・改善案）を永続保存
- セッションIDで管理（個人識別情報は保存しない）
- 保存先：S3（JSON形式）または DynamoDB

### FR-05: API

- API Gateway + Lambda によるバックエンドAPI
- エンドポイント1：`POST /generate-questions`（Phase 1 入力を受け取り、対応する Phase 2 質問リストを返す）
- エンドポイント2：`POST /analyze`（Phase 1/2 の対応ペアを受け取り、Phase 3/4 の結果を返す）
- レスポンス時間：`/generate-questions` は5秒以内、`/analyze` は15秒以内（Bedrock Opus 4.7 の生成時間を考慮）

## 非機能要件

### NFR-01: パフォーマンス
- Bedrock（Opus 4.7）生成は15秒以内
- フロントエンドの初期ロード：3秒以内（CloudFront キャッシュ活用）

### NFR-02: デプロイ環境
- AWS環境でエンドツーエンドで動作すること
- S3 + CloudFront でフロントエンドをホスティング
- Lambda + API Gateway でバックエンドを構成

### NFR-03: コスト最適化
- Claude Opus 4.7 はトークン単価が高いため、プロンプト設計でトークン消費を最適化
- 不要なコンテキストを削除し、必要最小限のプロンプトを設計

### NFR-04: データプライバシー
- 個人識別情報（氏名・連絡先等）は収集しない
- 保存データは匿名化（セッションIDのみ）
- GDPR/個人情報保護法への配慮（ハッカソン用途のため最低限）

### NFR-05: 可用性
- ハッカソンデモ用途のため、高可用性設計は不要
- Lambda + API Gateway の標準可用性で十分
